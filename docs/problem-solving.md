# 문제해결 사례

서비스의 주요 문제를 어떤 기준으로 나누고 구현·검증했는지 정리합니다.

## 1. AI 예측값을 그대로 사용하지 않는 구조

### 문제

AI가 혼잡 점수나 추천 후보를 직접 만들면 같은 입력에도 결과가 달라질 수 있고, 숫자의 근거를 설명하거나 경계값을 테스트하기 어렵습니다. 제공자 장애와 호출 비용도 핵심 기능에 영향을 줍니다.

### 선택

AI는 비정형 행사 정보를 구조화하고 계산 결과를 설명하는 역할로 제한했습니다. 점수, 후보와 정렬 순서는 결정론적 규칙 엔진에서 먼저 확정합니다.

### 구현

- [`calculateForecastScore`](../domain/forecast/score.ts)가 입력별 가중치와 보정을 합산하고 0~100으로 제한
- [`createAlternativeDecision`](../domain/decision/fallback.ts)이 방문 목적·장소 매력도·이동 부담·혼잡도를 계산해 후보 3곳과 순서를 확정
- [`requestStructuredAi`](../providers/ai-runtime.ts)가 제공자별 응답을 JSON으로 변환한 뒤 기능별 검증 함수 적용
- [`generateAlternativeDecision`](../providers/openai-decisions.ts)이 허용된 세 후보만 스키마에 넣고, 반환된 ID의 중복과 순서를 다시 확인
- 검증 실패나 제공자 오류가 발생하면 미리 계산한 규칙 기반 결과 반환

### 검증

테스트에서 점수 clamp와 위험 단계 경계, 대체 장소 3곳의 중복·선택 지역 제외·정렬 순서, AI 비활성 상태의 규칙 기반 응답을 확인합니다.

## 2. 여러 외부 서비스 중 일부가 실패해도 동작하는 파이프라인

### 문제

날씨·검색·행사·DB·AI를 모두 연결하면 한 서비스의 응답 지연이나 형식 변경이 전체 예보를 중단시킬 수 있습니다. 같은 행사에 AI를 반복 호출하면 비용과 갱신 시간도 불필요하게 증가합니다.

### 선택

출처별 실패를 격리하고, 저장 결과와 규칙 기반 기본값을 단계별 fallback으로 사용했습니다. 변경된 행사만 다시 분석하도록 원문 fingerprint를 도입했습니다.

### 구현

- [`collectEventCandidates`](../providers/event-discovery.ts)가 여러 행사 출처를 `Promise.allSettled`로 수집해 성공한 결과 유지
- 종료 행사 제외, 제목·시작일 기준 중복 제거, 날짜·장소·권역이 부족한 행사는 `needs_review`로 분리
- [`refreshEventDiscovery`](../providers/event-refresh.ts)가 원문 fingerprint를 비교해 신규·변경 항목만 분석하고 나머지는 저장 결과 재사용
- 동시 처리 4개, 실시간 AI 분석 최대 20건으로 호출 범위 제한
- [`GET /api/public/forecast`](../app/api/public/forecast/route.ts)이 Supabase 실패 시 기본 예보에 사용 가능한 외부 신호만 결합
- [`POST /api/internal/refresh-forecast`](../app/api/internal/refresh-forecast/route.ts)이 실행 잠금, 수동 실행 간격과 작업 이력 관리

### 검증

테스트에서 공공 API·검색·관광 페이지 응답을 같은 후보 형식으로 변환하는지, 같은 원문은 같은 fingerprint를 만드는지, 세부 날짜가 없는 장기간·다지역 행사를 자동 반영하지 않는지 확인합니다. 저장소와 AI가 없어도 공개 API와 혼잡 회피 결과가 반환되는 경로도 검증합니다.

## 3. 관찰 데이터가 부족한 예보를 과장하지 않는 방법

### 문제

혼잡 예보는 실제 현장 인원과 사후 관찰 자료가 충분하지 않으면 정확도를 입증하기 어렵습니다. 이 상태에서 ‘정확한 예측’이라고 표현하면 사용자와 심사자 모두에게 잘못된 신뢰를 줄 수 있습니다.

### 선택

결과를 실제 인원수가 아닌 상대적인 혼잡 가능성으로 정의했습니다. 혼잡 점수와 데이터 신뢰도를 분리하고, 관찰 표본이 쌓이기 전에는 적중률을 표시하지 않습니다.

### 구현

- UI에 점수 구성 요소, 행사 근거, 데이터 기준 시각과 한계 표시
- [`calculateConfidence`](../domain/forecast/confidence.ts)가 출처 품질·평시 데이터·검색·날씨·최신성을 별도 점수로 계산
- 관리자 검증 화면에서 행사 전 예보 스냅샷과 행사 후 관찰을 같은 양식으로 비교하도록 설계
- 완료된 관찰 자료가 없으면 정확도 수치를 생성하지 않음

### 검증

서버 렌더링 테스트에서 점수 근거와 한계 문구, 라이선스·데이터 출처, 검증 화면의 ‘정확도가 없으면 없다고 표시’ 원칙이 실제 HTML에 포함되는지 확인합니다.

## 면접에서 설명할 핵심

- AI를 많이 호출한 것이 핵심이 아니라 **AI가 변경할 수 있는 범위를 제한한 방식**
- 모든 외부 데이터를 신뢰한 것이 아니라 **실패·불완전·변경 가능성을 전제로 한 경계 설계**
- 정확도 수치를 만들지 못한 부분을 숨기지 않고 **현재 검증 가능한 불변 조건과 향후 검증 방법을 분리한 판단**
